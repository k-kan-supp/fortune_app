# G26 通知の時間帯

親: [集客戦略](../../growth.md) 視点26 ／ 関連: [M02](../monetization/02-subscription-daily.md) [G30](30-solar-term-alerts.md)

## ねらい

日次の運勢（`daily.py`）は**届く時間で価値が変わる**。
「今日の運勢」を夜に受け取っても意味が無い。朝の通勤時間帯が最も開かれるが、
生活リズムは人によって違うので、固定と個別最適の両方を用意する。
通知はリテンションに最も効く施策であり、同時に**最も嫌われやすい**。

## 実装

**backend**

- `app/services/notification/` を新設。予約と送信を分ける。
  **配信内容の生成はここに集約する**。LINE（[G17](17-line-official.md)）・
  メール（[G29](29-weekly-email.md)）・ウィジェット（[G28](28-home-widget.md)）は
  チャネル適応だけを持ち、内容を各自で組み立てない。
- 既定は7:30（JST）。ユーザーが変更できるようにする。
  最適時刻の自動学習は後回しで良い。まず選ばせる。
- **配信は1日1回を上限にする**。イベントごとに通知を足していくと、
  気づけば1日5通になって一括オフにされる。
  通知の種類ごとに個別のオンオフを用意し、まとめて切られないようにする。
- 送信失敗と無効トークンの掃除を入れる。
  無効なトークンに送り続けると配信基盤のコストが無駄になる。
- 通知の開封を [G34](34-analytics-foundation.md) に記録する。
  開封率が低い通知は止める判断ができるようにする。

**frontend**

- 通知の許可を求めるタイミングを設計する。**初回起動時に求めない**。
  日次の運勢を選んだ時点で求める。文脈がある時に求めると許可率が大きく変わる。
- 設定画面で種類別のオンオフ。
- ja/en 同時。

## 検証

- 1日の配信数が上限を超えないこと。
- 無効トークンが自動で除去されること。
- タイムゾーンが JST 固定で正しく動くこと。
- 種類別のオフが効くこと。
