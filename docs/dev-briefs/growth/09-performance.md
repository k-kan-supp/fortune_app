# G09 表示速度

親: [集客戦略](../../growth.md) 視点9 ／ 関連: [G31](31-fast-first-run.md) [G01](01-seo-free-tool.md)

## ねらい

検索から来た人の多くはモバイル回線。**表示が遅いと結果を見る前に離脱する**。
検索順位への影響もあるが、それ以上に [G31](31-fast-first-run.md) の
「30秒で結果まで」が物理的に成立しなくなるのが問題。
レーダーチャート10枚を描く画面なので、放置すると確実に重くなる。

## 実装

**frontend**

- まず測る。改善対象を決めずに最適化しない。
  Lighthouse を CI で回し、主要3ページのスコアを記録する。
- 想定される主要因:
  - チャートライブラリのバンドルサイズ。10枚描くために全機能を読み込んでいないか確認する。
    `RadarChart.tsx` の実装が自前なら問題ない。ライブラリ依存なら分割読み込みを検討。
  - `AnalysisCharts.tsx` が10枚を同時にマウントしている点。
    画面外のチャートは遅延描画にする。
  - フォント。日本語フォントを Web フォントで読むと極めて重い。システムフォントを第一候補に。
- 画像は `uploads/`（アバター）が主。適切なサイズで配信し、原寸を出さない。

**backend**

- `/api/fortune` の応答時間を計測してログに残す（`app/core/logging.py`）。
  10枚のチャート生成が遅いなら、そこが先。

## 検証

- Lighthouse のスコアを CI で記録し、閾値を下回ったら失敗させる。
- モバイルの実回線相当（低速）での結果表示までの時間を測る。
- バンドルサイズの上限をビルドで検査する。
