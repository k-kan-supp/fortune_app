# G38 CPA 上限

親: [集客戦略](../../growth.md) 視点38 ／ 関連: [G35](35-cohort-analysis.md) [G36](36-search-ads.md)

## ねらい

**これを決めずに広告を出すと、赤字を買い続ける**。
1人獲得あたりいくらまで払えるかは LTV から逆算する。
目安は CPA ≦ LTV/3。回収期間を考えると、この余裕が無いと資金繰りが回らない。
[G36](36-search-ads.md)〜[G39](39-app-network-ads.md) の全ての前提になる1本。

## 実装

**backend**

- `app/services/analytics/ltv.py`。
  [G35](35-cohort-analysis.md) の残存率と ARPU から LTV を推定する。
  - 継続課金は「残存率 × 月額」の累積
  - 都度課金は登録後N日以内の購入額の平均
  - **予測ではなく実績で計算する**。母数が少ないうちは実績12ヶ月分が無いので、
    暫定値であることを明示し、過信しない。
- 流入元別に LTV を出す（[G35](35-cohort-analysis.md) と同じ軸）。
  全体平均で判断すると、良い流入元と悪い流入元が打ち消し合って見えなくなる。
- CPA の実績を広告プラットフォームの費用と突き合わせる。
  費用の取り込みは手動で良い。自動化は後回し。

**運用**

- 上限を超えた流入元は止める。判断を人の裁量に委ねず、
  週次で機械的に見る仕組みにする。
- 母数が閾値（例: コホートあたり100人）未満の流入元は判断を保留する。

## 検証

- LTV 計算がテストで固定されていること（残存率と ARPU を与えて期待値）。
- 流入元別の合計が全体と整合すること。
- 母数不足の流入元が「判断保留」として区別されること。
