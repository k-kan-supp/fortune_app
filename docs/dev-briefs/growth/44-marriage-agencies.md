# G44 結婚相談所

親: [集客戦略](../../growth.md) 視点44 ／ 関連: [M48](../monetization/48-white-label.md) [G43](43-matchmaking-events.md)

## ねらい

結婚相談所は**会員のマッチングに悩んでいる**。
相性という切り口は紹介の根拠として使いやすく、会員への説明材料になる。
[G43](43-matchmaking-events.md) が単発の接点なら、こちらは継続的な関係で、
[M48](../monetization/48-white-label.md) のホワイトラベルに繋がる最有力の相手。

## 実装

**提供形態の判断**

1. 相談所向けの管理画面（自社ブランド）
2. ホワイトラベル（[M48](../monetization/48-white-label.md)）
3. API（[M47](../monetization/47-public-api.md)）
規模の小さい相談所は 1、大手は 2 か 3。まず 1 で始める。

**開発側**

- 相談所は**会員の個人データを大量に投入する**ことになる。ここが全て:
  - 会員本人の同意を、相談所経由ではなく本人から取得できる仕組みを用意する。
    相談所が一括同意する構造にしない。
  - データ分離（[M48](../monetization/48-white-label.md) の規律）を最初から入れる。
    相談所 A の会員データが B から見えない。
  - 契約終了時のデータ返却・削除の手順を実装する。運用の約束にしない。
- **相性スコアで会員を序列化しない**。[M46](../monetization/46-b2b-team-fit.md) と同じで、
  上位N件のリストを返す API を作らない。紹介の判断は相談所が行い、
  こちらは関係性の記述を提供する立場に留める。

## 検証

- 相談所間のデータ分離テスト。
- 本人同意の無い会員が計算対象にならないこと。
- 契約終了時の削除が完了すること。

- [ ] 本人同意が個別に取れる
