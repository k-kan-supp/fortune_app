# M25 製本・印刷

親: [マネタイズ設計](../../monetization.md) 視点25 ／ 関連: [M24](24-pdf-export.md) [M20](20-naming-reading.md) [M43](43-merch.md)

## ねらい

PDF（[M24](24-pdf-export.md)）を紙にして送る。命名（[M20](20-naming-reading.md)）や
節目の記念鑑定は**物として残る**ことに価値があり、単価が一桁上がる。
ただしここから先は物流が絡み、ソフトウェアだけでは完結しない。
**在庫を持たないオンデマンド印刷に限定する**のが撤退可能性を残す条件。

この指示書は**印刷・配送の基盤**を持つ。紙の商品そのもの
（カレンダー＝[M43](43-merch.md)、命名書＝[M20](20-naming-reading.md)）は各商品の指示書が持ち、
ここの `fulfillment/` を使う。商品ごとに住所テーブルを増やさない。

## 実装

**backend**

- 印刷会社の API に PDF と配送先を渡すだけの薄い連携にする。
  `app/services/fulfillment/` を新設し、印刷会社ごとの差異をここに閉じる。
- **配送先住所を持つことになる**。これは既存のどのデータより機微度が高い:
  - 発送完了後の保持期間を決めて自動削除する（例: 90日）。無期限保持にしない。
  - 住所を扱うテーブルは他と分離し、アクセス経路を限定する。
  - マイグレーションと同時に削除バッチも用意する。片方だけ入れない。
- 注文状態は `pending` / `printing` / `shipped` / `failed` を持ち、失敗時の返金経路を先に作る。
  印刷が失敗したのに課金だけ残る状態を作らない。

**frontend**

- 配送先入力は購入確定の**前**。後にすると入力途中の未確定注文が溜まる。
- 納期を明示。占いの製本は「いつ届くか」への期待値が高い。
- ja/en 同時。海外配送を受けないなら en 側で明示する。

## 検証

- 印刷 API 失敗時に自動返金が走ること。
- 保持期間経過後に住所が消えること（バッチのテスト）。
- 状態遷移が逆流しないこと。
