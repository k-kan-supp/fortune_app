# M40 手数料モデル

親: [マネタイズ設計](../../monetization.md) 視点40 ／ 関連: [M39](39-reader-marketplace.md) [M41](41-live-events.md)

## ねらい

**外部パートナーへの支払いを一元管理する**。
[M39](39-reader-marketplace.md) の出店者手数料だけでなく、
[M38](38-reader-referral.md) の送客報酬、[M41](41-live-events.md) の講師分配、
[M45](../growth/45-fortune-salons.md) の店舗還元も同じ台帳に載せる。
支払い先ごとに別実装にすると、端数処理と源泉徴収の扱いがばらついて必ず精算で揉める。

手数料率は一度決めると**下げることしかできない**（上げると離反する）ので、
やや高めから始めて下げる余地を残す。20〜30%が相場だが、
決済手数料を自社負担にするか相手負担にするかで実質が大きく変わる。

## 実装

**backend**

- `app/services/commerce/payout.py` に**パートナー種別を問わない**支払い計算を集約。
  **率をコードに埋めない**。パートナーごとに率を持てるようにする
  （初期出店者を優遇するなどの運用が必ず出てくる）。マイグレーション必須。
- 計算は「総額 → 決済手数料 → プラットフォーム手数料 → 出店者受取」の順を固定し、
  端数の丸め方向を明示する。ここが曖昧だと出店者との精算で必ず揉める。
  丸めは出店者有利（切り上げ）に倒しておくと運用が楽。
- 明細を出店者が自分で確認できる形で保存する。集計だけ持たない。
- 消費税・源泉徴収の扱いは税務確認を経てから実装する。個人の出店者が多いなら影響が大きい。

**frontend**

- 出店者向けの精算画面。1件ごとの内訳が見えること。
- ユーザー側には手数料を見せない。総額だけで良い。

## 検証

- 端数計算をテストで固定（率と金額の全組み合わせに近い形で）。
- パートナーごとの率が正しく適用されること。
- M38 / M39 / M41 / M45 の全種別が同じ計算経路を通ること。
- 明細の合計と入金額が一致すること。
