# M26 3段価格

親: [マネタイズ設計](../../monetization.md) 視点26 ／ 関連: [M27](27-decoy-plan.md) [M05](05-hybrid-billing.md)

## ねらい

480 / 980 / 1980 円の3段を敷く。段数を増やすと選べなくなり、
2段だと安い方しか売れない。**3が上限**。
重要なのは価格そのものより、**価格を1か所で定義してコードから消すこと**。
金額がテンプレートや文言に散ると、価格改定のたびに全画面を探すことになる。

## 境界

プラン間の**機能差の中身**（何がどう違うか、包含関係、差分の見せ方）は
[M27](27-decoy-plan.md) が持つ。この指示書が決めるのは
「価格とプラン定義がどこに存在するか」という置き場所だけ。

## 実装

**backend**

- `app/services/billing/catalog.py` に商品定義を集約する。
  `ProductCode` / `tier` / `features`（開放される機能コードの集合）/ `provider_price_id`。
  **金額そのものは持たない**。金額は決済プロバイダを正とし、表示時に取得する。
  自前で持つと必ずプロバイダ側とずれる。
- `entitlement.py`（[M05](05-hybrid-billing.md)）は `features` を見て判定する。
  プラン名で分岐しない。プランが増えるたびに条件式が増える構造にしない。
- `GET /api/billing/plans` でプラン一覧（機能の集合＋価格）を返す。
  フロントに価格表をハードコードさせない。

**frontend**

- プラン表は API の応答から組み立てる。
- 機能の差分だけを強調する。全機能を3列で並べると差が見えない。
- 通貨表記は i18n 側で処理。en で円表記のまま出さない判断も含めて決めておく。

## 検証

- 金額の文字列がコードベースに存在しないこと（grep ベースのテスト）。
- プラン追加時に `catalog.py` の1エントリ追加だけで済むこと。
- 機能コードの集合に重複・欠落が無いこと。
